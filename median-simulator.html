Does it really run in linear time?

    
Run each strategy on random arrays of growing size and count comparisons. If the algorithm is linear, comparisons per element stay flat as n grows. Sorting first would grow like log₂ n.

Why b matters: with b = 5 the two recursive calls cost n/5 + 3n/4 = 0.95n, which is below n, so the total is linear. With b = 3 they cost n/3 + 2n/3 = n, so the worst-case bound is only n log n. On random inputs the difference can be small, since the bound is about worst-case inputs. Random pivots usually use fewer comparisons in practice, but only median of medians guarantees linear time on every input.

      
The two-halves algorithm satisfies T(n) = 3T(n/2) + n, which grows like n1.58. Its cost per element keeps climbing, while sorting first costs about log₂ n per element, so for large n sorting beats it.

    

  


  
Conventions: t-th smallest (1 = minimum); the median is the ⌈n/2⌉-th smallest. In FIND, S₁ holds elements smaller than the pivot and S₂ larger ones. Equal values are ordered by position, so no two elements ever tie (in the two-halves algorithm this means m₁ ≠ m₂). The two-halves algorithm finds only the median, and its base case is at least 6 so that every recursive call is strictly smaller.
